# Trial 2: a 3D game, Aether mode against normal mode (2026-10-08)

**Question.** Trial 1 used a small plan whose tests pinned almost every behavior. Trial 2 repeats the comparison on a larger plan with frontend work, judged by the owner's four criteria: graphics quality, creativity, playability and 3D quality.

**Verdict: Aether mode was faster and cheaper again, but its quality was not equal.**
- 7.6 times faster: 18 min 06 s against 2 h 18 min;
- 5.3 times cheaper at OpenRouter prices: $4.17 against $21.95;
- graded 23/40 against normal mode's 32/40. Normal mode won all four criteria.

Both builds play correctly. Aether's passed 25/25 hidden cases and 12/13 browser checks; normal mode's passed 24/25 and 13/13. The gap is in what no test pins: the look, the 3D scene, the effects and the extras. The transcripts point to two causes, which this trial cannot separate:
- **Effort.** Aether's implementers run at a fixed `medium`. Normal mode's Sonnet implementers inherited the session's `xhigh`. On the five Sonnet tasks they worked 12 times as long and wrote 16 times as many output tokens.
- **Briefs.** Aether's briefs carried the plan's contract. Normal mode's controller added the spec's quality bar and the art direction to every render brief.

The cost ratio also compares unequal work: normal mode wrote 2.4 times as much game code. See [What this means for A9](#what-this-means-for-a9).

## Setup

**Fixture: Snake 3D.** A browser game built on three.js 0.186.1, with ES modules and no build step.
- [Spec](trial-2/fixture/spec.md). It says the game "should look and feel like a small, finished indie game, not a tech demo", and names the four criteria. Its "Look and 3D" section leaves the art direction to the builder.
- [Plan](trial-2/fixture/plan.md): a contract plan per A10, with 8 tasks across 3 areas (`core`, `ui`, `render`) in 3 waves:
  - wave 1: the rules, input, the high score, and the theme (the art direction);
  - wave 2: the HUD, the 3D world and camera, and the snake view with its effects;
  - wave 3: the game loop and the wiring.
- **Tiers:** three tasks are on Haiku, the pure logic. Five are on Sonnet: the art direction, the HUD, the 3D world, the snake view and the wiring, following the owner's rule that frontend work needs a stronger model.
- **Tests:** the plan's tests total 36. The render modules are tested structurally in Node with three.js: board size, camera framing, segment positions, interpolation and the head's heading.

**Evidence.**
- **The plan's tests**, and a [hidden suite](trial-2/fixture/acceptance-suite.js) of 25 cases on the rules and the structure.
  - The Designer wrote the suite before the runs, and neither session saw it.
  - A throwaway reference implementation passed all 25 hidden cases and all 36 plan tests. It was then deleted.
- **A [browser harness](trial-2/harness/evaluate-build.mjs):** headless Chromium with software WebGL (SwiftShader) plays each build through the `window.snake` debug API the spec requires.
  - The harness controls the page's clock, so the game runs exactly as in real time however slowly the frames draw.
  - An autopilot, a breadth-first search to the food, plays 40 seconds of game time with a fixed seed.
  - It runs 13 checks: the title screen, Enter to start, eating and growing, levelling up, pause and resume, game over at a wall, the high score, Enter to play again, and a phone screen without scrollbars.
  - It takes screenshots at fixed moments on a desktop (1280 × 720) and a phone (390 × 844), and records the frame rate and `renderer.info`.
- **Grading:** the builds were copied as A and B in random order, and graded against the rubric below before the key was opened. The blinding failed; see [Threats to validity](#threats-to-validity).

**Rubric** (1–10 per criterion, fixed before any build was seen):

| Criterion | 3–4 | 5–6 | 7–8 | 9–10 |
|---|---|---|---|---|
| Graphics quality | works; flat colors, default lighting | coherent palette, good light and shadows, readable | polished materials, post-processing used well, a cohesive HUD | striking, feels professional |
| Creativity | generic theme | recognizable theme, some touches | distinctive theme, several thoughtful effects, extras (sound, camera) | surprising ideas, well executed |
| Playability | playable with bugs | correct but plain | correct, smooth, clear feedback | excellent feel |
| 3D quality | basic boxes, default camera | solid 3D scene, shadows, smooth motion | rich 3D: modeled shapes, depth cues, effects in space | outstanding |

**Sessions.** Each mode ran once, in a fresh headless session (`claude -p`), one after the other:
- an Opus 5.5 main session at the owner's default effort (`xhigh`);
- superpowers 6.4.1 on;
- MCP connectors off;
- permissions bypassed;
- a $120 cap and a 4-hour timeout (neither was reached).

**Starting point.** Each mode got its own copy of the fixture, with the integration worktree `.worktrees/trial` already on branch `feature/trial` and its `node_modules` installed. The prompts are the same as in trial 1; the [harness](trial-2/harness) holds them with the scripts.

**Models per task.** As in trial 1, the normal-mode session read the plan's tiers and used them: Haiku implementers for tasks 1–3, Sonnet for tasks 4–8, Sonnet task reviews and an Opus final review. Both modes ran the same models per task, but not at the same effort; see [Where the difference comes from](#where-the-difference-comes-from).

**Cost figures.** The plugin prices at OpenRouter's rates (the owner's basis). Claude Code's own `costUSD` differs in one rate: it charges Sonnet 5.5 cache reads at $0.20 per million tokens, where OpenRouter charges $0.10.
- In this trial, that one rate explains the whole gap between the two figures, to the cent. Opus and Haiku match exactly.
- Trial 1's Sonnet figures show the same gap.

The table's OpenRouter figures price every request from the session transcripts, which record each request's cache-write lifetime ([price-transcripts.py](trial-2/harness/price-transcripts.py)). `aether-report price` works from Claude Code's per-model totals and has to assume the lifetimes. It came to $4.38 and $22.52; see follow-up 5.

**Aether build, "Midnight Neon"** ([title](trial-2/screenshots/aether-01-ready.jpg), [play](trial-2/screenshots/aether-02-play.jpg), [game over](trial-2/screenshots/aether-06-over.jpg)):
- **Graphics, 6.** A coherent neon palette and well-used bloom. The glowing cyan frame is the strongest element, and the three HUD panels match it. The materials are plain, the space around the board is nearly empty, and the phone view is mostly dark space.
- **Creativity, 5.** A recognizable neon-arcade theme with a few touches: a spark burst, a bloom pulse on level-up, and camera shake. No sound.
- **Playability, 7.** Correct and smooth, with clear feedback. One deviation: after a game over, Enter returns to the title screen, so a new game takes two presses although the hint says "Press Enter or tap to play again". The spec says Enter starts a new game at once ([`src/main.js`, line 148](trial-2/builds/aether/src/main.js#L148)). Neither the supervisors nor the final review caught it.
- **3D quality, 5.** A solid scene, with a shadow-casting light and smooth, interpolated motion. But the snake is a row of boxes, the food is an orb with a ring, and the space around the board holds only a sparse starfield.

**Normal build, "Abyssal Bloom"** ([title](trial-2/screenshots/normal-01-ready.jpg), [eating](trial-2/screenshots/normal-03-eat.jpg), [game over](trial-2/screenshots/normal-06-over.jpg)):
- **Graphics, 8.** A deep-sea scene with low-poly rock walls, caustic light on the board, glossy materials and well-tuned bloom. The HUD's glass panels and its copy carry the theme ("Lost to the deep", "dive again", "The tide holds still").
- **Creativity, 8.** A distinctive theme carried through everything:
  - a glowing eel for the snake, and an amber anglerfish lure for the food;
  - plankton, bubbles and pulse rings;
  - on game over, the scene dims and tints red;
  - a drifting camera on the title screen;
  - synthesized sound, muted with `m`.
- **Playability, 8.** Correct and smooth, with clear feedback and careful input: held keys do not repeat, a 600 ms grace stops a held key from restarting the game, and it respects reduced motion. It failed one hidden case: when time goes backwards, the loop's progress drops to 0 instead of holding ([`src/loop.js`](trial-2/builds/normal/src/loop.js)). Browsers' frame clocks never go backwards, so a player cannot see it.
- **3D quality, 8.** Modeled shapes (a tube eel, rocks, kelp), depth cues from fog and layered decor, and effects placed in space.

The normal scene costs more to draw: 12 times the triangles, and 40% of the frame rate in software rendering. On a real GPU both should be smooth, but neither was measured on one.

**The owner's view of the Aether build**, given after playing it and before the normal run finished:

> "Lo veo bien, es un juego tradicional pero muy seguro, no apuesta por cosas extremas ni powerups es un juego clasico con estilo modernizado pero estable, no diria que es creativo o experimental, pero dependiendo de lo que se busque esta bien o mal, en este caso lo veo bien y funcional"

In short: good and functional, a classic snake with a modern, stable style, safe rather than creative or experimental. This agrees with the grades.

## Where the difference comes from

**Quality: two causes, which this trial cannot separate.**

**1. Effort.** Aether's agent definitions fix each role's effort: `medium` for implementers, `high` for supervisors and the final reviewer, `low` for ops. Normal mode's Sonnet and Opus subagents inherited the session's `xhigh`, and its Haiku subagents ran at `medium`. On the five Sonnet tasks (the art direction, the HUD, the world, the snake view and the wiring), the implementers worked like this:

| Task | Aether implementer, `medium` | Normal implementer, `xhigh` |
|---|---|---|
| 4, the theme | 22 s, 4 requests | 2 min 09 s, 10 requests |
| 5, the HUD | 31 s, 5 requests | 8 min 22 s, 36 requests |
| 6, the world and camera | 53 s, 6 requests | 12 min 25 s, 44 requests |
| 7, the snake view | 3 min 56 s, 6 requests | 21 min 29 s, 76 requests |
| 8, the loop and wiring | 1 min 09 s, 14 requests, two attempts | 38 min 28 s, 105 requests, with its fix round |
| **Total** | **6 min 51 s, 29,000 output tokens** | **82 min 53 s, 459,000 output tokens** |

Output tokens include thinking, so effort shows up directly in them. The reviews differ the same way. Aether's supervisors took 8 to 48 s each, and its final review 2 min 37 s. Normal mode's task reviews took 47 s to 4 min 38 s, and its final review 14 min 12 s.

**2. What the brief carries.**
- **Aether.** `aether-plan compile` writes each brief from the task's text and the plan's Global Constraints, so the plan's goal does not reach the swarm.
  - The render implementers did read the spec section their task names, such as "Look and 3D". That section leaves the art direction to the builder.
  - The spec's opening sets the bar ("a small, finished indie game, not a tech demo") and names the four criteria. Of the five Sonnet implementers, only the wiring task's read it.
  - The supervisors check each diff against the brief and that section.
- **Normal mode.** Its Opus controller wrote a brief of 5,000 to 13,000 characters for each render task:
  - it put the bar and the four criteria first;
  - it passed the theme's art-direction notes from task 4 to tasks 6–8;
  - it passed tuning advice from earlier reviews, such as emissive intensities against the bloom threshold.

To see how much each cause matters, rerun Aether mode on this fixture, changing one of the two at a time.

**Speed.** Aether ran its waves in parallel, and its agents worked briefly. Normal mode is serial by design, and its five Sonnet implementers alone took 83 minutes.

**Cost.** The same two causes, plus the amount of work:
- **Effort and context.** Normal mode's Sonnet agents ran at `xhigh`, in long sessions whose context grew with every step: 41 million cache-read tokens, and 74 prompts over 200,000 tokens. Sonnet is 62% of normal mode's cost. Aether's Sonnet agents never passed 25,000 tokens of prompt.
- **Less work in Aether.** Part of the saving came from building less: normal mode built 2.4 times the game code. Trial 1's cost comparison was at equal output; this one is not.

## What this means for A9

- **Trial 1 passed A9:** faster and cheaper at equal quality on the spec.
- **Trial 2 holds for speed and cost, but not for equal quality on work judged by taste.**
  - The correctness evidence is close: 25/25 against 24/25 on the hidden suite, and 12/13 against 13/13 in the browser.
  - The judged quality is not close: 23/40 against 32/40.
- **Both candidate causes are settings of the plugin:** the implementers' fixed effort, and what a brief carries. Both changes are small; see the first follow-up.
- **A fair next step:** make the changes, then rerun Aether mode on this fixture and compare it with this normal run. A rerun at higher effort will cost more than this one did, and still far less than the normal run.

Whether A9 stands as passed, or waits for that rerun, is the owner's decision.

## Threats to validity

- **Sample size:** one run per mode. Creative output varies a lot between runs.
- **Blinding failed.** The normal build shows its theme's name, "Abyssal Bloom", on its title screen. The Designer had seen that name in the normal run's commits while monitoring it, so the grades were given knowing which build was which. Mitigations:
  - the rubric was fixed before any build was seen;
  - the screenshots and both builds are in the repository, for anyone to grade again;
  - the owner's own view of the Aether build agrees with its grades.
- **One grader**, who also wrote the fixture.
- **The fixture pinned the classic rules**, with no power-ups or new mechanics. Creativity could show only in the look, the effects and the sound, as the owner noted.
- **Run conditions:** headless, permissions bypassed, connectors off.
- **The frame rates** come from software rendering, so they compare the two builds and say nothing about a real GPU.
- **A first Aether run was discarded.** `claude -p` stops background work 10 minutes after the last turn, and it stopped the first run during its final review (see the [research notes](../claude-code-research.md)). That run cost $2.17 and took 10 min 38 s. The run reported here is the rerun, on a fresh fixture, with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`.

## Follow-ups

1. **Effort and intent for work judged by taste.** Two changes, to test one at a time on this fixture:
   - **effort:** let the plan set an implementer's effort per task, instead of the fixed `medium`. For example, a Sonnet task judged by taste would run at `xhigh`;
   - **intent:** `aether-plan compile` adds the plan's goal and the spec's statement of purpose to every brief. The plan states its quality bar in Global Constraints, which every brief already carries. The supervisor and the final reviewer judge against both.
2. **A browser check in the final review of a UI plan.** It would have caught the two-press restart, which no test pinned.
3. **Flush the meter before the report reads it.** The meter writes every 20 requests and at the end of a turn. `finalize` ran in the middle of the Designer's last turn, so the record stopped at the last flush, 3 minutes earlier. The Designer reported a session of 14 min 33 s and $3.43; the session took 18 min 04 s and cost $4.17. A flush whenever the oldest buffered request is older than about 30 seconds would close most of the gap.
4. **A scratch folder for the Designer that the code sweeps.** The plugin sweeps the units' temporary files, but not the Designer's own. The Designer left five scratch paths in `/tmp`, 1.5 MB: compile and report output, browser-check scripts and screenshots. Normal mode left 18 paths, 4 MB. The swarm skill should give the Designer a folder inside the run directory, and `finalize` should delete it.
5. **Exact cache lifetimes in the report.** The transcripts record each request's cache-write lifetime; `turn.step`'s usage does not.
   - In this trial the meter's rule held exactly: 1 hour for the main session, 5 minutes for agents. So the record's run-window cost matched the transcripts to the cent.
   - `aether-report price` reads Claude Code's per-model totals, which mix the Designer's Opus requests with the Opus final reviewer's. It priced them all at 1 hour and came out 5% high for Aether mode.
   - In the Plan 3 smoke run, the rule itself was off by 3%.
   - Reading the lifetimes from the transcripts would make every figure exact.

## Playing the builds

Both builds are kept exactly as each session committed them, without `node_modules`:

    cd docs/evaluations/trial-2/builds/aether    # or builds/normal
    npm ci
    npm start                                    # http://localhost:8080/
    PORT=8083 npm start                          # when port 8080 is busy

`npm test` runs each build's own tests. To replay a fixed game, add `?seed=7` to the URL. The harness needs `playwright-core` 1.64 and Playwright's Chromium:
- `setup.sh <mode>` builds a fixture;
- `run.sh <mode>` runs a session;
- `evaluate.py <mode>` measures it;
- `blind.py <dir>` makes the blind copies;
- `evaluate-build.mjs <build> <out> <label> <port>` plays one build in the browser.
