# Components

Every piece of the Aether plugin and what it does, and the footprint of Aether in a session that is not in Aether mode; the method they serve is in [Methodology](../methodology.md), and the options that change them are in [Options](../guide/options.md#options).

## The pieces

| Piece | What it does |
|---|---|
| `using-aether` skill | Injected at session start. The Lead's rules: its role, RADAR, the method on Spec Kit's layout, the clarifying questions, the intent card and `/aether:design` with what to do for each of its four results, the exam, assumptions, the owner's list, the three paths (direct, delegate task, swarm) and the choice of model for each delegate task, fallbacks, the rules of autonomous runs that hold outside a run (the irreversible classes, the grants, the repetition rule and the short brief) and the execution method |
| `autonomous-runs` skill | The Lead's procedure for a run of hours, loaded when the owner gives permission to work for hours or session start reports an open run: the start, the permission warnings, the diary, the rule of working on, the ceilings, the cost record, when a run is done, the honest stop, resuming and the brief |
| `aether:lead` | The Lead agent: the main session of Aether mode, started with `claude --agent aether:lead --effort xhigh`. It is not a subagent. It starts on Sonnet, and its rules are the `using-aether` skill's |
| `aether:writer` | The Writer agent: Sonnet at `high`. It writes `spec.md` from the intent card, and `plan.md` and `tasks.md` from the approved spec, with the Aether fields and a `Serves` line on each task, and checks them with `aether-plan check`. An external Writer in a seat runs at its pair's effort |
| `aether:judge` | The Judge agent: Opus at `high`, read-only. It reviews a spec, a plan or tasks, and rules `approve`, `revise` or `reject`, with at most ten findings, each typed `missing`, `extra` or `wrong`: what goes beyond the owner's intent is a defect, as much as what is missing |
| `aether:examiner` | The Examiner agent: Opus at `high`. It writes the hidden acceptance exam of an approved spec and plan under `.aether-exam/`, one command per test, without reading `tasks.md` |
| `aether-lane` | The commands of superdelegation: `status`, `pick`, `start`, `wait`, `result`, `stop`, `took`, `pause`, `quota` and `delegate`, which choose the pair for a call, run it on another harness's model, log which one took it, read each harness's quota, and run an editing delegate in a unit worktree. Whether a run uses them depends on the `superdelegation` option, off by default; see [Options](../guide/options.md#options) and [Lanes](../guide/lanes.md#lanes) |
| `aether-lane seat` | One round of a design seat (`judge`, `writer` or `examiner`) on the external pair the rule of [Lanes](../guide/lanes.md#lanes) chooses when `superdelegation` is on, in a disposable worktree of the commit; exit 3 or 4 hands the round to the native agent. The Judge and the Examiner take a pair of another family first, then the author's own family, and the native agent only last; the swarm and `aether-lane delegate` still bar the author's family. `/aether:design` runs a round in steps instead: `aether-lane seat-start` launches it, `seat-wait` waits for it within one ops call and `seat-stop` ends it |
| `aether-route` | Decides how each delegate task of the Lead runs: `begin`, `finish` and `decide` for the router, `delegate` to run a read-only delegate on agy, grok or muse, `spawn` to record which agent ran a delegation, so that the delegates report can price it, `replay` over the history, and `renew` to renew the quota reading of agy or grok in the background |
| `aether-exam` | Keeps an exam outside the repository (`store`), runs it on a commit in a disposable worktree (`run`), and lists the kept ones (`list`) |
| Aether preset | `plugins/aether/speckit/`: Spec Kit's specify, plan, tasks and constitution commands adapted to Aether, also shipped as the skills `aether:specify`, `aether:plan`, `aether:tasks` and `aether:constitution` |
| `aether-voice` | Prints the owner's own words from a session, so a quote can be checked; it writes no file |
| `aether-first-setup` | Installs a small command that starts Aether mode, `aeth` by default (`--name`), in `~/.local/bin` by default (`--dir`). The command is a stub of POSIX sh with a marker line that runs the launcher of the newest installed release each time, so it never goes stale; only a version directory shaped like `0.12.3`, with a launcher that is an executable file, counts. A name is at most 64 characters, and not `claude`, which the launcher runs. It replaces only a stub of its own: a file of that name that is not one, or a command of that name on the `PATH`, makes it write nothing and exit 3. It never edits a shell file; when the directory is not on the `PATH` it prints the line to add for bash, zsh and fish. `--check` writes nothing. It prints one JSON object, and exits 2 on a usage mistake |
| `first-setup` skill | `/aether:first-setup`, which the person calls once after installing, in a plain session. It sets `disable-model-invocation`, so the model never loads it on its own. It has Claude run `aether-first-setup --check` and then `aether-first-setup`, ask once for another name when the name is taken, and tell the person the command to type and the line for the `PATH` |
| `onboard` skill | `/aether:onboard [topic]`, which the person calls at the start of a session to have Claude understand the project before asking for anything. It sets `disable-model-invocation`, so the model never loads it on its own, and it only reads: the README and `CLAUDE.md`, `git status` and the recent log, the newest handoff, the branches, worktrees and pull requests, the feature that `.specify/feature.json` points to and an open autonomous run. It ends with a brief of 5 to 8 lines and the question of what to do, and starts no work. Where the handoff and git disagree it goes by git, and it reports an open run that belongs to another session without continuing it |
| Launcher | `plugins/aether/launcher/aether-lead`: Claude Code with the Lead as the agent, at `xhigh`, with permissions bypassed, superpowers off, the Aether theme in the session's own settings and `AETHER_IRREVERSIBLE=enforce`. It is outside `bin/` so that it is not on the Bash tool's `PATH`. `scripts/aether-lead` in a clone forwards to it, and the stub of `aether-first-setup` runs it. See [Getting started](../getting-started.md#start) |
| `aether-guard` | A PreToolUse hook. In an Aether session it refuses Write, Edit, MultiEdit and NotebookEdit on specs, plans and tasks (`specs/NNN-<topic>/`, and the old `docs/superpowers/`) and on the constitution to every agent but the Lead and the Writer, on the autonomy registry and run states to every agent, and on everything outside `.aether-exam/` to the Examiner. Before Bash, it records an irreversible command that no grant covers in the owner's list, `.aether/pending.jsonl`, and refuses it when `AETHER_IRREVERSIBLE=enforce`. In any other session it allows everything |
| `aether-autonomy` | The owner's standing authorizations, verified against their own words (`grant`, `revoke`, `check`, `list`), and an autonomous run's state and ceilings (`start`, `spend`, `status`, `end`) |
| `swarm` skill | The Lead's procedure: compile, launch, read the result, report, relaunch, finalize |
| `aether-plan` | Checks a plan and compiles it into briefs and a dependency graph of waves, and records the run's test baseline. It reads a Spec Kit `tasks.md`, and the `spec.md` beside it. It refuses chain-shaped plans, and waves whose tasks own overlapping files |
| `aether-wt` | Unit worktrees and branches: `ensure`, `diff`, `merge` (ownership check, then the tests; undone if they fail), `salvage` (commits what a unit that ended without its report left, and writes its package), `adopt` (records a unit the Lead integrated by hand), `remove` (saves unmerged work as a patch), `sweep` |
| `/aether:design` | The design workflow: from the intent card in `specs/NNN-<topic>/intent.md` to an approved spec, plan and tasks and the exam, with the Writer, the Judge and the Examiner in seat rounds and at most two revisions per document, and one result, `approved`, `clarify`, `dispute` or `failed`. It needs the Workflow tool |
| `/aether:run` | The workflow: waves, the escalation ladder, the agent budget, the merge queue, the final review (which also flags what is extra), and cleanup in `finally` |
| Agents | `implementer`, `supervisor`, `reviewer` (adapted from superpowers' templates, MIT) and `ops` |
| Usage meter and ops | A mod that records every model request of an Aether session: agent, model, tokens and time. It also runs the workflow's own `aether-wt` and `aether-lane` commands itself, without a model, and calls the router (`aether-route`) (see [Ops without a model](../guide/ops.md)). Since 0.12.3 it also declares the `/harnesses` command, a read-only pane of the delegation settings and the quota of each harness (see [the panel](../guide/lanes.md#the-harnesses-panel)). In any other session it records and runs nothing, declares no command, and does not offer Aether's agents |
| `aether-report` | Reports a run's speed, cost and quality; `finalize` records the run; its seats mode counts the design seats' rounds and who answered them; `price` prices any `claude -p` JSON output |
| `aether-session-start` | The command that the SessionStart hook runs. It acts only for the Lead: in any other session it prints nothing and writes nothing |
| SessionStart hook | In an Aether session: marks the session and passes the `superdelegation` and `harnesses` options to its commands; on startup, clear and compact, but not on resume, it also injects the bootstrap, sweeps runs left untouched for 24 hours, deletes usage files, lane logs and session markers not written to for 30 days, and points a new Lead to an open autonomous run. In any other session it does nothing |

## What Aether adds to a normal session

Today, in 0.14.0, the plugin has the eleven commands of `bin/`, and they are on the Bash tool's `PATH`; the measurement below, taken at 0.7.0, counted eight.

Measured on Claude Code 2.1.296 with Aether 0.7.0, on 2026-10-09 (`docs/evaluations/2026-10-09-installable/A3-dormant.md`), in a session started without `--agent aether:lead`, against the same session with Aether disabled:
- the first request grows by 431 characters, all in the first message: the `aether:run` and `aether:swarm` entries of the skills list;
- the system prompt and the tools are unchanged;
- `claude plugin details` estimates about 100 tokens always on;
- the commands of `bin/` are on the Bash tool's `PATH`;
- each session start, and each `Write`, `Edit`, `MultiEdit` or `NotebookEdit` call, runs one short `node` process that finds no Aether session and exits.

Nothing is injected, refused, recorded or written. Versions 0.8 to 0.12 were not measured this way. They add four things, read from the plugin and not measured: the entries of the four preset skills (`aether:specify`, `aether:plan`, `aether:tasks` and `aether:constitution`) in the skills list, whose descriptions are 459 characters; the entry of the `aether:autonomous-runs` skill, added in 0.11.0, whose description is 223 characters; the same short `node` process before each `Bash` call; and, since 0.12.0, a mod hook before each `Agent` call that checks the session marker and, in a session that is not Aether's, hands the call on unchanged. Version 0.12.3 adds nothing at the start of a plain session: the `/harnesses` command is declared only in an Aether session, so in any other nothing of the panel is injected, written, recorded or run.

The `first-setup` skill, the `aether-first-setup` command and the launcher add nothing at the start of a plain session, and this too is read from the plugin, not measured. The skill sets `disable-model-invocation`, which in Claude Code's documentation keeps a skill's description out of the model's context, so it adds no entry to the skills list; `claude plugin details` still counts about 30 tokens for it, as it does for `using-aether`, which sets the same field. `aether-first-setup` is one more file on the Bash tool's `PATH` and runs only when called, with no hook. The launcher is outside `bin/`, so it is not on the `PATH`, and it runs only when the person starts it. The `onboard` skill sets the same field, so it too adds no entry to the skills list, runs no hook and adds no command; this is read from the plugin, not measured.
