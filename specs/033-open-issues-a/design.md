# Design: a read-only delegate on another harness reads what the Lead could read (issues #198 and #185)

- **Feature:** `specs/033-open-issues-a`
- **Author:** the Lead (Fable 5.2), 2026-11-11. Revision 6 answers the two findings and the question of the Judge's review 2 of this round: the exclude pathspecs of D1 are rooted with `top` and no longer start with `/`, D5 skips no system folder but `/dev`, `/proc` and `/sys`, and its comparisons go through `realpath`. Revision 5 answered the fourth review's eight findings. Revision 4: the copy keeps the repository's history, which the owner chose after the third review asked for his decision. It keeps what the first two reviews settled (the scan in `begin`, `AETHER-TREE:`, the records on the `outcome` entry, the fake's export verb, the fixed identity) and answers the third review's four findings.
- **Route:** short design. It sends uncommitted files of the owner's checkout to another provider's model, so it touches security, and it copies a tree the Lead may be editing, so it touches concurrency.
- **Scope:** read-only delegates of the Lead on agy, codex, grok and muse (`plugins/aether/lib/delegate-calls.js`). Editing delegates, swarm units and design seats are out: they build on a commit and are merged from it.

The Lead recommended the history, as what «lean lo mismo que tu podrias leer» asks, and named its cost. ## What happens today, read against 0.38.0 (`42c792f`)

- `runDelegate` in `lib/delegate-calls.js` runs the harness's CLI in a disposable worktree made of the `HEAD` of the Lead's current checkout (`git worktree add --detach <worktree> <HEAD>`, in `<main>/.aether/work/delegates/<id>/wt`), judges it from outside (`worktreeChanges(worktree, start)`: any change undoes the answer) and removes the worktree. That worktree shares the repository's object store and history, so the delegate reads `git log` and every committed file, a committed `.env` among them.
- Step 2 of `runDelegate`: when the checkout has uncommitted paths (`uncommittedPaths`, from `git status --porcelain`), it returns the outcome `dirty` before anything is read or launched, and the task runs on Claude. Issue #198 measured 43 `dirty` outcomes in 127 read-only tasks; in 27 of them the only uncommitted file was `CLAUDE.md`. Nothing stale is read, but one read in three goes back to Claude's quota.
- The copy is always of the checkout the Lead's shell is in. Issue #185: a brief that said to work in another worktree was answered about the Lead's current one (an inventory of release 0.25.1 that read as complete), and a brief about folders outside the repository was answered about the copy only. That second case is the stale read the owner calls a serious design flaw.
- Every harness but Codex runs with its approvals off and no sandbox (`--dangerously-skip-permissions` in agy, `--disable-approval` in muse, `--force` in cursor), so the disposable copy is what keeps a delegate from writing in the owner's checkout. That protection stays. It is no sandbox for reading: see the accepted limits.

## Criteria

- **C1** A read-only delegate is launched on another harness when the checkout has uncommitted work, and its copy holds that work: the changed content of tracked files, staged changes, new files that git does not ignore, and no file that was deleted. The copy keeps the repository's history, as today.
- **C2** Files that git ignores are never in the copy. A new file whose name is `.env` or begins with `.env.` is not in the copy, and neither are the uncommitted edits of a tracked one: the copy holds the committed content of a tracked `.env`, as today, and taking the copy writes no git object with the content of a new or edited `.env`.
- **C3** Taking the copy changes nothing of the Lead's working tree, index, stash, branches, `HEAD` or `git status`: they are the same before and after. Its object store gains only objects that no ref reaches.
- **C4** A brief can name the tree it is about with a line `AETHER-TREE: <path>`: a worktree of the same repository. The copy is then of that tree, with its uncommitted work. Without the line, the copy is of the Lead's current checkout, as today.
- **C5** A brief whose subject the copy cannot hold is not sent out: it names, in the Lead's own words, an existing path outside the tree being copied, or an existing path inside it (written absolute or relative) that git ignores or that is a `.env` file. The task runs on Claude, which reads the real paths, and the delegate log says why. No partial answer that reads as complete.
- **C6** A delegate that changes its copy still has its answer undone, measured from the copy as it was given.
- **C7** `npm test` and `npm run test:mod` pass. The existing tests that pin the `dirty` refusal are rewritten to the new behaviour, and only those (`tests/delegate-calls.test.js` lines 70-102 and 202-204; `tests/delegate-chain.test.js` line 171 stubs a `dirty` outcome and stays): the copy's directory and the count of worktrees do not change, so the tests that pin them stay.

## Design

**D1. The copy is the same linked worktree as today, detached at a snapshot commit.** The directory does not move: `<main>/.aether/work/delegates/<id>/wt`. In the tree to copy, with `GIT_INDEX_FILE` set to a new file in the delegate's own work directory (`<main>/.aether/work/delegates/<id>/index`), three steps build the snapshot. `GIT_INDEX_FILE` is set in the environment of the git calls of these steps only; it is never in the environment of `git worktree add`, `git status` or any other git call of `runDelegate`, so the new worktree's checkout writes its own index and not the temporary file:
1. `git read-tree HEAD`: the temporary index is exactly `HEAD`, whatever the Lead has staged. It carries no stat data, so step 2 reads and hashes every tracked file on each launch; this cost is accepted (see the limits) rather than seeding the cache from the Lead's index, which would make that index a source.
2. `git add -A -- . ':(exclude,glob)**/.env' ':(exclude,glob)**/.env.*'`, with one more exclude pathspec for each of Aether's own directories that git does not already ignore in that tree (see below): every change of the working tree enters the temporary index (edits, deletions, and new files that `.gitignore`, `info/exclude` and the global excludes do not ignore), except any path whose base name is `.env` or starts with `.env.`, at any depth, and Aether's own directories (the entries of `run.EXCLUDES`, read from that list, not written by hand). Each entry `/<name>/` is kept out in one of two ways, decided by `git check-ignore -q -- <name>` run at the root of the tree being copied. When git already ignores the directory, which is the normal case because `run.ensureExcluded` wrote its line, no pathspec is passed for it: `git add -A` leaves an ignored directory out by its own rule. When git does not ignore it (`ensureExcluded` threw, or the line is gone), the entry becomes the pathspec `:(exclude,top)<name>/`: its leading `/` is removed, because a pathspec that begins with `/` is an absolute filesystem path to git, and `top` roots it at the tree's root, so a folder of the same name deeper down, such as `deep/.aether-tmp/`, stays visible, as `run.EXCLUDES` says. Both ways are needed because git refuses the other combination: an exclude pathspec that names a directory git ignores makes `git add` stop with «The following paths are ignored by one of your .gitignore files». Revision 6 passed the three pathspecs always and had tried them only on a tree where the directories were not ignored; its first build failed in almost every launch (12 of the 17 tests of `tests/delegate-calls.test.js`), and the implementer stopped and reported it. What was observed on git 2.53.0: by the Lead, on a tree without the ignore lines, the three pathspecs exit 0 and leave the three directories out of the tree that is written; by the implementer, on a tree with the ignore lines, the same pathspecs exit 1. That an `add -A` without those pathspecs leaves an ignored directory out is git's ordinary rule, and the tests below hold it. Either way the directories do not depend on `run.ensureExcluded` having written the ignore lines: if it throws, the exam under `.aether/exam/`, the files of other delegates and the temporary index itself still never enter the snapshot, and no object with their content is written, because the exclude acts when the files are added. The pathspecs are rooted at the tree being copied, so a tree named by `AETHER-TREE:` has its own folders of those names excluded the same way. A tracked file that an ignore rule also matches is still updated: ignore rules apply to untracked files only.
3. `git write-tree`, and, when that tree differs from the tree of `HEAD`, `git commit-tree <tree> -p HEAD -m 'aether delegate snapshot'`, with fixed `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` (`aether-delegate`, `aether-delegate@localhost`) in its environment, so a machine without `user.name` or `user.email` still launches. `commit-tree` runs no hook.

The worktree is then added detached at that commit (`git worktree add --detach <worktree> <snapshot>`), or at `HEAD` when the trees are equal: a clean tree, or one whose only changes are `.env` files, makes no commit. No ref points at the snapshot commit: it leaves with the worktree and git prunes it later. The temporary index is deleted in the same `finally` that removes the worktree. The Lead's own index is never read as a source and never written: `read-tree`, `add` and `write-tree` all act on the temporary one.

**D2. `.env` files: what is uncommitted stays out.** The exclude of D1 acts when the files are added, so the content of a new `.env` file, or of an uncommitted edit to a tracked one, is never hashed into the object store by the snapshot: there is no blob of it to find, dangling or not. In the temporary index a tracked `.env` keeps the content of `HEAD`, because `read-tree HEAD` put it there and the `add` does not touch it; so the copy holds the committed `.env`, as today, and never its edit. A new `.env` is absent. The count of `.env` paths left as they are in `HEAD` or left out is taken with `git --no-optional-locks status --porcelain -z -- ':(glob)**/.env' ':(glob)**/.env.*'` run in the tree being copied (it takes no optional lock and does not write the Lead's index), counting its entries; it is the field `envHeldBack` of the `outcome` entry (D7), a number, never a content or a name. If the owner had staged a `.env` himself, that blob exists by his own `git add`; the snapshot does not reference it.

**D3. The check measures from the snapshot.** `start`, which `worktreeChanges(worktree, start)` compares with, is the commit the worktree was added at: the snapshot, or `HEAD`. Nothing else of the judging changes.

**D4. The tree.** `AETHER-TREE:` is parsed next to `AETHER-TASK:` in `lib/delegate-task.js`. `begin` writes it into the external file as its own field `tree`, apart from `cwd`: `cwd` stays the Lead's checkout, which `delegate-run.js` uses for the unit branch and the integration worktree, and `tree` is the directory to copy; `runReadOnly` hands `tree` (or `cwd` when there is none) to `runDelegate`. The snapshot of D1 is built in that tree, on that tree's `HEAD`. A path that is not a worktree of the same repository (`git worktree list --porcelain` from the Lead's checkout) refuses the launch with a message that names the worktrees, as an unknown skill in `AETHER-SKILLS:` does. A task with `AETHER-OWNS:` ignores the line: this design is for read-only tasks. When `tree` no longer exists at run time (the worktree was removed between `begin` and the run), the attempt ends as `failed` and the task goes to Claude; `runReadOnly` never falls back to `cwd` for a missing `tree`, as `delegate-run.js` does for a missing `cwd`, because that would copy the Lead's checkout and answer about the wrong tree, which is issue #185 again.

**D5. What the copy cannot hold.** `begin` decides this once, before it picks a pair, on the text of the Lead's own prompt: the brief as the Lead wrote it, without its `AETHER-` lines, and never `externalPrompt` (which adds the earlier-work sections, the findings and the bodies of the skills). The words are taken like this: split on white space; strip from each word the backticks, quotes, brackets and parentheses around it, trailing `.`, `,`, `;`, `:`, `!` and `?`, and a suffix `:LINE`, `:LINE:COL`, `:LINE-LINE` or `#LINE`. A word is a candidate when it starts with `/`, `~/`, `./` or `../`, or has a `/` inside it. A candidate is expanded (`~/` to the home directory, a relative one against the tree being copied) and counts only if it exists on disk. The candidate, or its nearest existing parent with the rest appended, and the tree's root both go through `realpath` before any comparison below, so a checkout reached through a symbolic link, or a `/tmp` that is a link, does not mark every path `outside`. `--show-toplevel` is already a physical path and is compared with the root's `realpath`. Then:
- an existing path that is not inside the tree being copied is `outside`;
- an existing path inside the tree whose own repository top level (`git -C <its directory> rev-parse --show-toplevel`, the directory being the path itself when it is one, else its parent) is not the tree's root is `outside`: a nested repository or a worktree under the tree, such as `<checkout>/.claude/worktrees/x/file`, is held by the copy only as a link, or not at all;
- an existing path inside the tree, written absolute or relative, is turned into a path relative to the tree's root and is `outside` when `git check-ignore -q` says it is ignored (the case `<checkout>/.worktrees/x/...` of issue #185) or when its base name is a `.env` name: a task about a `.env` file is not sent to another provider, committed or not.

The first such path goes into the detail. A candidate that is a device file or lies under `/dev`, `/proc` or `/sys`, and the exact command words `/usr/bin/env`, `/bin/sh` and `/bin/bash`, are skipped, so `/dev/null` or `#!/usr/bin/env node` in a command of the brief do not send it to Claude. No other system folder is skipped, `/tmp` and `/var` among them: a brief about the Lead's scratch files in `/tmp` is about files the copy does not hold, which is issue #185. A word that does not exist on disk is not a path for this rule, which keeps a URL's path and a command such as `/aether:run` from matching. When `begin` finds `outside`, nothing is launched on another harness and no quota is read: the task runs on Claude at its step's model, and the launch line of the log carries `outside: <path>`. `runDelegate` receives no such task, so it has nothing to decide per candidate pair. It no longer returns `dirty`; readers of old log lines keep understanding it.

**D6. What the delegate is told.** `DELEGATE_NOTE` says the current directory is a copy of the tree taken at launch, with its uncommitted changes in one commit on top of the repository's history (`git show HEAD` shows them when there are any), without the files git ignores and without new `.env` files or uncommitted edits to them, and that an absolute path of the brief under that tree is under the current directory.

**D7. Records.** The snapshot does not exist when `begin` writes the launch line, which `begin` writes before `runDelegate` runs, in another process. So the snapshot's facts (the tree, whether it carried uncommitted work, and `envHeldBack`, the number of `.env` paths held back, as counted in D2) go on the `outcome` entry that `delegate-chain.js` writes after the call. The launch line gets only what `begin` knows: `outside: <path>` when D5 applied, and the tree named by `AETHER-TREE:`. `docs/guide/delegates.md` says what a read-only delegate on another harness reads. The Lead's bootstrap gets one line, because the Lead learns the brief lines only from the list under `## The delegate ladder` of `skills/using-aether/SKILL.md`: «`AETHER-TREE: <path>`: a read-only task about another worktree of the repository; the delegate reads a copy of that tree with its uncommitted work.» Each part of the bootstrap stays within 9,800 characters, which the existing test of the parts holds (`tests/session-start-parts.test.js` lines 92-100 measure it at a long folder path: the new line is run through that test and the part that holds it is checked at that length, not assumed); the system still decides what runs where, and the Lead only names the tree.

## Accepted limits

- **The history travels, as today.** Whatever is committed in the repository, or ever was, can be read in the copy through git: a `.env` file that was once committed, too. The owner accepted this on 2026-11-11 (see «The history» above). What this design adds to today is only the uncommitted work of files that are not `.env` files.
- **The copy is not a sandbox for reading.** A harness that runs with its approvals off and ignores the rule to work only in its directory can read the owner's real files, the real `.env` among them, by an absolute path. That is so today and stays so; option C, which would close it, was declined. The copy stays under the checkout for that reason: moving it to the system's temporary folder would not stop an absolute path, and would change the paths that the existing tests pin.
- The snapshot is of the moment of launch. What the Lead edits while the delegate reads is not seen. A file being written at that instant may be copied half written.
- A new file that is not ignored and is not a `.env` file travels to the other provider, whatever it holds. Today the same file travels once it is committed.
- The path scan of D5 is by words: a brief that describes a place without writing its path is not caught.
- The snapshot's objects (the blobs of the changed files, its trees and its commit) stay in the object store, reached by no ref, until git prunes them.
- A nested repository inside the tree is not copied: git records it as a link, not as files.
- Every launch hashes every tracked file of the tree again, because the temporary index has no stat data. The cost grows with the size of the tree and is accepted: seeding it from the Lead's index would make that index a source, which C3 forbids.
- A brief whose only path is a device or the three command words of D5 (`/dev/null`, `/usr/bin/env`, `/bin/sh`, `/bin/bash`) is sent out. Every other existing path outside the tree, `/etc/hosts` or `/usr/lib/x` among them, sends the task to Claude: the cost is a task that could have gone out and stays on Claude, which is the safe side.
- Other files that may hold secrets (`.envrc`, `.npmrc`, key files) travel like any other new file: only `.env` names are held back, as the owner named only `.env`. Widening the list is a later decision of his.
- `git add` runs the clean filters the repository configures, as any `git add` of the owner's does.

## Tests

In the style of `tests/delegate-calls.test.js` (throwaway repositories from `tests/helpers.js`, a fake adapter, no real CLI), written first and seen failing.

The tests that look inside the copy use a new verb of `tests/fixtures/fake-agy.js`, `FAKE-AGY: export <absolute-dir>`, which copies the files of its current directory (not `.git`) to that absolute directory in the test's own temporary folder, and writes there the output of `git log --format=%s -3`, `git show --stat HEAD` and `git cat-file --batch-all-objects --batch` run in its current directory: `runDelegate` removes the copy in its `finally`, so the test reads what the fake exported.

1. A checkout with a changed tracked file, a staged file, a new file, a deleted file, an ignored file, a new `.env.local` holding the marker `NEW-ENV`, and a tracked `.env` whose committed content holds `OLD-ENV` and whose uncommitted edit holds `EDIT-ENV`: the delegate is launched; its exported copy holds the first three as they are on disk and lacks the deleted, the ignored and the `.env.local`; its `.env` holds `OLD-ENV` and not `EDIT-ENV`; the exported output of `cat-file` holds neither `NEW-ENV` nor `EDIT-ENV`; `git log` in the copy shows the snapshot commit on top of the repository's last commit; the outcome's `envHeldBack` is two. The same with the identity removed for real: `git config --unset user.name` and `git config --unset user.email` on the repository (`makeRepo` writes them into its local config), `user.useConfigOnly true` set, and `GIT_CONFIG_GLOBAL` pointing at an empty file, so that a `commit-tree` without the fixed `GIT_AUTHOR_*` and `GIT_COMMITTER_*` fails and the test fails with it. The same with `info/exclude` made unwritable or without the lines of Aether's directories, and a `.aether/exam/secret.txt` in the checkout: no `.aether` path is in the exported copy or in the exported `cat-file` output. Every other case of these tests runs with the three directories ignored, as `run.ensureExcluded` leaves them, and with a file under `.aether/` in the checkout: the launch succeeds and that file is not in the copy, which is the normal case that revision 6 failed. In both cases a `deep/.aether-tmp/file` of the checkout is in the copy.
2. The Lead's `git status --porcelain`, the hash of its index file, its stash list, its branches and its `HEAD` are equal before and after, and `git worktree list` in the Lead's repository is the same after the call as before it. With the Lead's own index holding a staged `.env` edit, the copy still holds the committed `.env`.
3. A clean checkout: the copy is at `HEAD` and `git count-objects -v` is the same before and after (no commit is made). A checkout whose only change is an edited `.env`: the same.
4. `AETHER-TREE:` with another worktree of the repository, which has uncommitted work of its own: the copy is of that worktree, with that work. With a path that is not one: the launch is refused and names the worktrees. With a `tree` removed after `begin`: the attempt is `failed` and the Lead's checkout is not copied.
5. In `begin`, with the Lead's brief naming: an existing path outside the tree; an existing ignored path inside it, relative and absolute (including `<checkout>/.worktrees/x/file`, with `.worktrees/` ignored); an existing `.env` path, committed or not: each gives `outside`, the launch line records the path, the task is on Claude, no pair is picked and no quota is read. The same path written as `/x/a.js:120`, in backticks, in quotes, in parentheses and with a trailing full stop is found in the same way. A path that appears only in the earlier-work sections or a skill body does not give `outside`. An existing, not ignored path inside a nested repository or a worktree under the tree (`<checkout>/.claude/worktrees/x/file`): `outside`. A brief with a URL, with `/aether:run`, with `/dev/null` and with `/usr/bin/env`: launched. The existing path outside the tree is made with `tempDir` too, a folder of its own that is not inside the tree's `tempDir`, so that it lies under `os.tmpdir()` as the tree does: it gives `outside` and is not skipped. A `~/file` that exists in the test's home (`SCRATCH_HOME`, also under the temporary folder) gives `outside`. The tree reached through a symbolic link, with an existing path inside it written through the link, is not `outside`.
6. A delegate that edits its copy: `violation`, with the files it touched, measured from the snapshot, so the Lead's uncommitted work is not counted as the delegate's.
7. The external file written by `begin` for a task with `AETHER-TREE:` holds `tree` and keeps `cwd` as the Lead's checkout. The snapshot's facts are on the `outcome` entry, not on the launch line.
8. The tests that pin the `dirty` refusal are rewritten (`tests/delegate-calls.test.js` lines 70-102 and 202-204), and `tests/delegate-chain.test.js` line 171 stays as it is.
9. The existing tests that assert the copy's directory (`.aether/work/delegates/<id>/wt`) and the count of worktrees pass unchanged.
